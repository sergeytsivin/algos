ПРАВИЛА ОФОРМЛЕНИЯ УЧЕБНЫХ ЗАДАЧ ДЛЯ СЕМИНАРОВ

1. Назначение набора

Каждый набор задач должен быть посвящён одной алгоритмической теме и рассчитан
на один-два семинара. Задачи нужны не только для проверки знания алгоритма, но
и для последовательного знакомства с ключевыми идеями темы.

Перед подготовкой набора следует сформулировать:

- какую основную идею должны освоить студенты;
- какие вспомогательные приёмы они должны применить;
- чем каждая следующая задача отличается от предыдущей;
- какие типичные ошибки должен выявлять набор.

2. Структура каталога

Для каждой темы создаётся отдельный каталог с коротким названием в стиле
kebab-case, например branch-and-bound.

Рекомендуемая структура:

  topic-name/
    README.md
    solutions.md
    01_short_name.cpp
    01_short_name.txt
    01_short_name.expected.txt
    02_short_name.cpp
    02_short_name.txt
    02_short_name.expected.txt

Номер задаёт порядок прохождения задач. Одинаковая основа имени связывает
условие в README.md, эталонное решение, пример входа и ожидаемый результат.

3. README.md семинара

В начале README.md указываются:

- тема и учебная цель семинара;
- предполагаемая продолжительность;
- общие соглашения, действующие во всех задачах;
- требования к языку и версии стандарта;
- особенности ограничений или представления данных.

Для каждой задачи приводятся следующие части:

1) короткое название;
2) ясное условие без лишней легенды;
3) точное описание требуемого результата;
4) ограничения на все входные величины;
5) формат входных данных;
6) формат выходных данных;
7) допустимая неоднозначность ответа, если решений несколько;
8) учебная цель задачи;
9) список относящихся к задаче файлов.

Форматы ввода и вывода оформляются отдельными блоками. Индексация, свойства
графа, наличие петель, кратных рёбер и другие неочевидные соглашения должны
быть оговорены явно.

4. Последовательность задач

Задачи располагаются по возрастанию сложности идеи и реализации. Каждая новая
задача должна добавлять один существенный элемент, например:

- переход от проверки существования к поиску ответа;
- восстановление решения;
- оптимизацию вместо задачи разрешимости;
- взвешенную версию;
- новую оценку, эвристику или структуру данных.

Не следует включать несколько задач, отличающихся только легендой или
незначительной деталью ввода. Связь между соседними задачами полезно описывать
прямо в README.md, но полный алгоритм раскрывать там не нужно.

5. Условия и ограничения

Условие должно допускать только одну содержательную трактовку. Все специальные
случаи необходимо определить: пустой ответ, отсутствие решения, несколько
оптимальных ответов, нулевые размеры и граничные значения.

Ограничения выбираются под предполагаемый алгоритм. Они должны:

- отсекать заведомо слишком медленные подходы;
- оставлять разумный запас по времени и памяти;
- соответствовать типам данных эталонного решения;
- помогать студенту распознать ожидаемый класс сложности.

Если полный перебор не является целью задания, это следует сказать явно.

6. Разбор решений

Подробные идеи и доказательства помещаются в solutions.md, отдельно от условий.
Разбор каждой задачи должен содержать:

- ключевое наблюдение или сведение;
- состояние алгоритма и смысл его параметров;
- переходы или правила ветвления;
- доказательство корректности;
- оценку времени и памяти;
- способ восстановления ответа, если он требуется;
- типичные ошибки и важные крайние случаи.

Разбор следует начинать с идеи, а не с кода. Необходимо объяснять, почему
алгоритм работает и откуда берётся его сложность. Эталонная реализация не
заменяет доказательство.

Сначала следует давать самое простое решение, которое укладывается в
ограничения и раскрывает основную идею темы. Дополнительные оптимизации нужно
выносить в отдельный подраздел solutions.md и предлагать студентам для
самостоятельной проработки. Следует описать идею таких оптимизаций, ожидаемый
эффект и условия применимости, но не добавлять их реализацию в эталонный код.

7. Эталонные решения

Для каждой задачи предоставляется отдельное решение на C++17. Код должен:

- компилироваться в режиме C++17 и не требовать возможностей более новых
  стандартов;
- точно соответствовать опубликованному формату;
- компилироваться без предупреждений с -Wall -Wextra -Wpedantic;
- использовать простое решение без лишних классов, шаблонов и уровней
  абстракции;
- реализовывать только базовый разобранный алгоритм, без дополнительных
  оптимизаций, оставленных для самостоятельной проработки;
- использовать короткие и привычные для алгоритмических задач имена переменных,
  например n, m, v, g, dp и used;
- не содержать не относящихся к теме оптимизаций;
- корректно обрабатывать крайние случаи;
- иметь сложность, соответствующую заявленным ограничениям.

Все комментарии в коде пишутся на русском языке. Они нужны для объяснения
нетривиальных инвариантов и решений, а не для пересказа каждой строки
программы. Краткость имени не должна делать его двусмысленным: для сущностей,
чья роль не ясна из контекста, следует выбрать более точное имя.

8. Примеры и проверка

У каждой задачи должен быть как минимум один запускаемый пример:

- NN_short_name.txt содержит входные данные;
- NN_short_name.expected.txt содержит точный ожидаемый вывод.

Пример должен проверять содержательную часть алгоритма, а не только чтение
входа. Для задач с несколькими допустимыми ответами пример не заменяет общих
тестов: эталонный файл фиксирует один ответ, но условие обязано разрешать любой
корректный ответ.

Перед публикацией набора необходимо:

1) собрать все эталонные решения;
2) запустить их на приложенных примерах;
3) сравнить вывод с файлами expected.txt;
4) проверить минимальные и максимальные граничные случаи;
5) убедиться, что условие, разбор и код используют одинаковые соглашения.

9. Стиль изложения

Текст пишется на русском языке, короткими и однозначными предложениями.
Обозначения должны быть единообразны во всём наборе. Имена файлов, фрагменты
ввода, вывода и кода выделяются моноширинным оформлением в Markdown-файлах.

В условии не следует заранее выдавать полное решение. Допустимо назвать
изучаемую тему и сформулировать учебный переход между задачами. Детальное
сведение, доказательство и реализация относятся к solutions.md и обсуждению на
семинаре.

10. Критерий готовности

Набор готов, если студент может по README.md однозначно понять каждую задачу и
проверить программу на примере, а преподаватель может по solutions.md провести
разбор ключевых идей, корректности, сложности и типичных ошибок.
